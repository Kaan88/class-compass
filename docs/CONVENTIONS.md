# Engineering Conventions (read before changing code)

These patterns are established in S0/S1 and every stage must follow them. If a pattern must change, record it in DECISIONS.md and update this file.

**Adding a module or a theme:** follow `docs/EXTENDING.md` (checklists, plus `npm run new:module -- <key>` and `npm run new:theme -- <key>` scaffolds; D-069, D-070). Agents start with the root `AGENTS.md` (D-159).

## Runtime & tooling
- Node 26 runs TypeScript directly (type stripping). **Only erasable TS syntax**: no `enum`, no `namespace`, no constructor parameter properties. Use `as const` objects and union types.
- Relative imports include the `.ts`/`.tsx` extension. `import type` for type-only imports (`verbatimModuleSyntax`).
- `npm run check` = typecheck + lint + tests. It must be green before every commit. `npm run build` must succeed.
- Commit messages: `<stage>: <summary>` and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Layout & boundaries (lint-enforced)
- `src/shared` — contracts (Zod endpoint definitions), i18n, Turkish text utils. Imports only `shared`.
- `src/domain` — pure logic (rotations, week math, grouping solver, metrics, name parsing). No I/O. Unit + property tests (`fast-check`).
- `src/server/modules/<module>/{manifest,routes,service,repo?,policy?,commands?}.ts`. The module's `manifest.ts` (`defineServerModule`) is the only place that wires routes, commands, lesson hooks and config, and it is listed once in `src/server/modules/index.ts` (D-069). The client mirror is `src/client/modules/<module>/manifest.tsx`, listed in `src/client/modules/index.ts`. Module policy keys come from `src/shared/modules.ts` only.
- `src/client/...` — React. Never imports server code.

## Database
- Tables in `src/server/db/schema.ts` (append a section per module). Conventions are in the file header: UUIDv7 text ids (`newId()`), epoch-ms UTC `...At`, local dates as `'YYYY-MM-DD'` text computed in the class timezone, `{en,tr}` JSON for teacher-editable labels, soft archive/void instead of delete.
- After schema changes: `npm run db:generate -- --name <stage_desc>` and commit the SQL in `drizzle/`. Never edit an already-committed migration. Check generated SQL: SQLite table rebuilds must not cascade-delete data.
- Writes that must be atomic use `tx(db, fn)` (synchronous; never `await` inside).
- Names are sorted in application code with `sortByName`/`compareNames` (never `ORDER BY name`).

## HTTP API
- Every endpoint is declared once in `src/shared/contracts/<module>.ts` with `endpoint({method, path, access, input, output})` and registered with `route(app, deps, ep, handler)`. Output schemas are allow-lists: never return rows directly when they contain fields the caller must not see.
- Access classes (`define.ts`, `ACCESS_CLASSES`): `public | user | account | classroom | teacher | admin | student | scorer | display | mcp | oauth`. `mcp` (S14h1, D-160) is the AI tools endpoint `/mcp`: a bearer token only, never a cookie; a bearer token is refused on every other class. `oauth` (S14h2, D-160) is only for the OAuth protocol endpoints of the MCP module (discovery, register, authorize, token, revoke): no cookie, no CSRF header, an Origin on a POST must be the main origin, OAuth's own formats; never use it for anything a browser session does (the consent itself is `account`). `scorer` and `display` (S12, D-128) are Super Speakers link sessions with their own cookies; take the link from `requireScorer(ctx)` / `ctx.display`, never from the request. Classroom-safe actions (taps, attendance, stage changes) are `classroom`; anything showing reports, private notes, roster edits, settings, links is `teacher`/`admin` (PIN-gated in classroom mode server-side).
- Resource authorisation is done in services with policy helpers (e.g. "teacher owns this teaching context", "teacher teaches in this class"). Never trust ids from the client without checking ownership. Student principals get `studentId` from the session only.
- Temporary passwords (D-040): an account with `mustChangePassword` can only use `user` endpoints and endpoints declared with `allowWithTemporaryPassword: true` (the password change). Do not add that flag to anything else.
- Errors: throw `AppError(code, message, details?)`. Stable codes in `ErrorCodes`. Put a machine-readable `details.reason` (e.g. `YEAR_ARCHIVED`, `POSSIBLE_DUPLICATE`) on business conflicts and add a matching `error.<REASON>` i18n key.
- **School policy helpers** (`src/server/modules/school/policy.ts`) — reuse them, never re-implement: `assertTeachesClass(ctx, classId)` (teacher has an active context in the class), `assertOwnsContext(ctx, contextId)` (returns the context; ACC-10), `assertYearWritable(db, yearId)` / `assertClassWritable(db, cls)` before **any** write touching a class or year (archived = read-only, DAT-1; `isClassWritable` when one of several classes must be writable), `todayFor(deps, cls)` for local dates in the class timezone. Enrolments are date-aware (D-027): use `enrolmentActiveOn(date)` (fromDate <= date < toDate) for "who is in this class on day D" — never `toDate IS NULL` alone — and `defaultEnrolmentDate(deps, cls)` for new enrolments.
- **Module gating** (`src/server/modules/school/modules.ts`): `isModuleEnabled(db, contextId, module)` / `assertModuleEnabled(...)` before serving or accepting module data; `getMediaPolicy(db)` before accepting photo/audio/document uploads (D-014, D-026). Disabled modules keep their data.
- **Uploads and files** (S9, D-076): an endpoint whose body or response is not JSON (multipart upload, file download) is still declared with `endpoint()` and registered with `rawRoute(app, deps, ep, handler)` from `lib/http.ts`: access is checked before the body is read and the input comes from path + query only. Take uploads only through `ingestUpload(ctx, req, { kind, ownerStudentId })` (`modules/files/service.ts`): streamed size limit per kind, content sniffing against `ALLOWED_MIME` (never the client's type or name), image re-encoding, quotas in the insert transaction, audit. Check media flags with `assertMediaAllowed` first. Never serve upload bytes from anywhere but `sendFile()` after `assertCanReadFile()`; never put a storage key or path in a response. The one markup exception is the importer's HTML-table `.xls` (`application/x-cc-html-table`, `import_source` only, `.xls` name, read only by `import/parsers/html.ts` in the parser worker, never served as HTML; D-171): do not add it to another kind or read such a file anywhere else.
- **Student photos** (D-077): never send `photoFileId` to the client; build the URL with `photoUrlOf(student, getMediaPolicy(db).studentPhotos)` (null unless photos are on, consent is recorded and there is a photo), and render it with `Avatar photoUrl=… photoAllowed=…`.
- **Students**: create via `createStudentInClass` (students service) so names are normalised, duplicates flagged and enrolments opened consistently (teacher, admin, seed, importer). Modules that must act on every new student register with `onStudentCreated(listener)` from the students service (runs inside the creating transaction, synchronous; the links module uses it to give each student a permanent link, D-115). Classroom endpoints return only `id, fullName, initials, avatarHue`; levels and numbers are teacher-access only (GRP-7).
- Optional services (mail) are injected through `AppDeps` (`deps.mailer`) so tests can pass fakes.
- Classroom mutations that must survive flaky Wi-Fi go through **commands**: declare them with `command({...})` in the module's `commands.ts`, export them as a list and put the list in the manifest's `commands` (only manifests register commands, test-enforced; D-069). Handlers are synchronous, run inside the transaction, re-verify ownership and lesson/context consistency, and may use `meta.opId` as the id of the row they create.
- Important edits write `audit(db, ctx.actor, {...}, ctx.now())` in the same transaction (never include secrets or pre-reveal Secret Student identities).
- Time: use `ctx.now()` (injectable clock), never `Date.now()` in services.
- **Intl formatters and collators (S15a, D-162).** Never construct an `Intl.DateTimeFormat`, `Intl.Collator` (or call `localeCompare` / `toLocale…String` with a locale) per call in server, shared or domain code: use `localDate` (`domain/dates.ts`), the shared date texts (`formatDate`, `formatDay`, `formatWeekRange`) or the cached `dateTimeFormat` / `collator` / `compareTr` (`shared/intl.ts`); names sort with `compareNames`. Long jobs (exports, purges, digests) work in bounded pieces and `await yieldToEventLoop()` (`lib/yield.ts`) between them; a read that yields and must be consistent uses `openReadSnapshot` (`db/client.ts`).
- **Lesson-scoped commands** (S5, D-044): a command that records something in a lesson carries `contextId` + `lessonId` in its payload (and the outbox envelope). Resolve the lesson with `lessonForCommand(ctx, payload, meta)` from `modules/lessons/service.ts`; it throws `WRONG_LESSON` / `LESSON_ENDED`. Change lesson rows only through `updateLesson` (bumps `version`, which feeds the polling ETag). Attendance writes go through `setDailyCore` / `setExceptionCore` (roster check + audit).
- **Module hooks into lessons** (D-051, D-052, D-069): modules declare End Lesson steps with `endLessonStep({key, order, module, input, apply})` in their server manifest's `endSteps` (runs inside the end transaction; order < 100 runs before the core reflection; `module` must equal the manifest's `policyKey`) and the matching screen with `endStepUi({...})` in the client manifest's `endSteps`. Dashboard slots (boxes or dock buttons of the classroom board, S14b) and Start Lesson steps (each adds its part of the one `lesson.start` command through `useContribution`) go in the client manifest's `dashboardSlots` / `startSteps`; screens read them through `src/client/modules/registry.ts` and never name a module. A start step that must write something on the server puts its input under `steps[<key>]` and declares `startLessonStep({key, module, order, input, onResume?, apply})` in its server manifest's `startSteps` (S14b, D-149; runs after the start-screen attendance, `onResume` ones also when the start resumes a running lesson; `useStartContributions` merges `steps` key by key). Orders are unique per list. Never render a placeholder for a module that has not declared anything.
- **Lesson close and attendance hooks** (D-067): a module that must react when a lesson ends or is abandoned lists the hook in its manifest's `lessonCloseHooks`; one that reacts to attendance lists it in `attendanceListeners`. Both run inside the writing transaction, so keep them synchronous and small. Small per-context module settings are declared as the manifest's `config: { schema, defaults }` (Zod), are validated on every write (`setContextModule` and `mergeModuleConfig`, `INVALID_MODULE_CONFIG`) and services read them with `moduleConfig(db, contextId, module)` (`modules/school/modules.ts`; defaults replace invalid stored values), not with `getModuleConfig` and not in new tables. A settings screen is the client manifest's `settingsPanel`.
- **Grouping boundary** (D-073, GRP-7): levels, arrangement modes, pair rules, their notes and unsatisfied-rule details (and their count, S13a) are teacher-access only. Classroom responses about groups carry names, icons, members, roles and member counts only. A new classroom GET must keep `tests/server/grouping.test.ts` (marker-string scan of every classroom GET) green.
- **Idempotent REST batches** (D-074, D-075): a non-lesson write that may be retried and undone (homework marks) takes an optional client `batchId` (UUID). A repeated batch is replayed, not applied twice. Each change row stores before/after values under the batch, so `…/undo {batchId}` can restore it and skip rows changed since.
- **Secret Student boundary** (D-064): only `server/modules/secret/` may import or query `secretSelections` (test-enforced). Before the reveal, any value it returns, audits, logs or puts into an ETag stamp must be a count. A new GET endpoint is automatically included in the differential leak scan (`tests/server/secret-leak.test.ts`), so keep that test green and do not exempt routes from it.
- **Student link sessions** (S10, D-084): `student` endpoints see ONLY the student cookie (`ccs` / `__Host-ccs`) and every other access class sees only the teacher/admin cookie (`contextFor`), so a browser holding both never mixes them. Take the student id from `requireStudent(ctx).studentId`, never from the request, and scope reads with `studentScope(deps, studentId)` (`modules/links/scope.ts`: classes the student is in today, their active contexts). Someone else's record answers 404; the student's own record written by a teacher answers 403 `NOT_YOUR_CONTRIBUTION`. Student-visible files are served only by `/api/student/files/:id` through `assertCanReadFile` (own upload, or a file on the student's own live evidence). Responses to students carry no author ids, private notes or other students.
- **Student page sections** (S10, D-085): a module adds a section to the personal student page with its server manifest's `studentPage: [{ key, order, build(ctx, { studentId, context, cls }) }]`; `key` and the returned shape must be a member of the shared `StudentPageSection` union (`shared/contracts/goals.ts`, an allow-list), and its home tiles and screens are registered in `src/client/student/sections.tsx` (`STUDENT_SECTIONS`, type-checked: every key needs an entry; tile order in `TILE_ORDER`). The links module calls only the contributions of modules enabled for that class+subject.
- **Student page screens** (S14d, D-151): the page is a home screen of tiles plus short-step screens. Screens live in the query string (`student/nav.ts`: `screen`, `subject`, `goal`, `step`; `go`, `back`, `finish`), never in the fragment, which carries the link token; a new screen goes into `SCREENS`, unknown values fall back to home. A step that needs an earlier choice the screen no longer has (a reload) goes back to the first step that is missing; a saved flow calls `finish(target)`. Every screen has one h1 with id `student-screen-title` (the focus moves there on each change). Text hints on the student page show when Save/Next is pressed (`useSaveCheck` in `student/common.tsx`), not while typing; deletes ask with `ui/InlineConfirm.tsx`, never `window.confirm`. `npm run build` checks the student bundle's gzip budget (`scripts/student-budget.ts`); add no libraries to it.
- **Goal category names (S22b, D-176).** A default skill category keeps its row and id; a teacher's own name for it in one subject is a `goal_category_names` row. Show or snapshot a category's name only through `categoryName(row, categoryNamesOf(db, teacherId, subjectId))` (`goals/library.ts`) with the teacher of the class+subject being shown (the library, the student page, lesson topics, reports, goal label snapshots; `goalDtos` uses each goal's own class+subject); never read `skill_categories.name` for display elsewhere. Group and count by the category id, never by the name.
- **Private teacher notes** (GOL-6, D-086, D-114): only `server/modules/goals/private.ts` reads or writes `private_teacher_notes` (plus the boolean history check and the full-export rows `exportablePrivateNotes` in `goals/history.ts`), and only the teacher Goals service imports it (test-enforced in `tests/server/goals.test.ts`, which also scans every student response for a note). Only the admin's full export includes notes; the per-student export never does.
- **Report sections and timeline** (S11, D-091): a module adds a report section through its manifest's `reports` and student-timeline events through `timeline` (see EXTENDING). Cells come only from `modules/reports/cells.ts`: every count carries its denominator, "not recorded" / "absent" / "not in the class" are their own cells (never 0, RPT-5), no overall score. Reports are `teacher` (own contexts via `reportableContext`, an ended assignment limited to the days it was held by `heldPeriod`; 423 while locked) or `admin` (no lesson reflection notes, usage report without student data). CSV goes through `tableCsv` (BOM, formula escaping) and is audited.
- **Report views and user settings** (S14e1, D-153): a report section declares its tables in its contribution's `meta` (EXTENDING); views (built-in in `shared/reportViews.ts`, saved per account in `report_views`) travel as the report's `sections` parameter, and screens link to a report with the deep-link parameters `contextId`, `studentId`, `view`, `period`, `from`, `to` (`linkSearch` in `reports/ReportsPage.tsx`). Preferences that follow an account across devices are user settings: declare the key once in `USER_SETTINGS` (`server/lib/userSettings.ts`, a Zod schema and a default) and read/write only with `getUserSetting` / `setUserSetting` (invalid stored values fall back to the default). Never put student data or secrets in a user setting; per-device conveniences stay in `localStorage`.
- **Teacher notifications (S14e3, D-155).** A write that records something a student did (or that happened to a student) which a teacher may want to see later calls `notify(ctx, { category, studentId, subjectId, entity, entityId, actorUserId? })` from `lib/notify.ts` inside its transaction, after the write: ids only, never text, never a pre-reveal Secret Student identity. It is a separate emitter, never called from the activity hook (the achievement rules would recurse). The notifications module's sink decides the recipients (current teachers of the student and subject, module on, category on, never `actorUserId`); nothing else reads or writes `notifications`. A new category goes into `shared/notifications.ts` (`NOTIFICATION_CATEGORIES`, `DEFAULT_ON`, `CATEGORY_MODULE`, `NOTIFICATION_GROUPS`) with `notifications.category.*` / `notifications.item.*` keys, a snippet rule in `notifications/service.ts` if it points at student text (re-checked at read time: hidden, deleted and blocked text never shows), and a case in `tests/server/notifications.test.ts`. The daily digest carries counts only.
- **Classroom student card** (S14e2, D-154): what the class may see about one student comes only from the server manifests' `classroomCard` (EXTENDING); a new item needs a member in the shared `ClassroomCardItem` union (`shared/contracts/classroomCard.ts`, an allow-list of positive things: never attendance, homework, goals or student text, levels, Secret Student data, notes, ranks or comparisons) and a renderer in `modules/lessons/board/StudentCardDialog.tsx`. The card endpoint answers 404 for anything but the teacher's own running class+subject and a student in the class today; keep `tests/server/classroom-card.test.ts` green.
- **Downloads** (S11): a file response (CSV, export ZIP) is a `rawRoute` whose input comes from path + query; the client links to it with `urlFor(endpoint, input)` from `lib/api.ts`, never by building the path by hand. Exports are written to `DATA_DIR/exports/` under a random token and deleted after one download or an hour.
- **Operations boundaries** (S11, D-089, D-090, D-094): backups, restore and off-site copies live in `src/server/ops/` and are driven by the CLI and the maintenance module; backup commands never migrate (only start-up and `migrate` do) and restore refuses a database another connection holds (`databaseInUse`); only `ops/restic.ts` runs restic, with a filtered environment, and every text from it passes `redact()`. Storage credentials come from the environment only and are never logged, stored or returned. Generic exports never name `secret_selections` or `private_teacher_notes`: they use the owning module's helpers (`exportableSelections`, `privateNotesCount`, `exportablePrivateNotes`). Encrypted secrets (`…_cipher` columns, e.g. `student_links.token_cipher`) are blanked like `…_hash` columns; encrypt with `sealSecret(pepper, purpose, aad, text)` from `lib/crypto.ts` (own HKDF purpose per use, the row id as AAD), never with an ad-hoc key. Destructive admin actions need a typed confirmation and an audit row; maintenance actions also need the admin's PIN.
- **Link sessions for scorer and board** (S12, D-128, D-129): new link-based principals follow the student-link pattern: fragment token, HMAC lookup (`tokenHash`), encrypted copy (`sealSecret` with its own purpose), one exchange endpoint (rate-limited, refused attempts counted per address) that sets a strict HttpOnly cookie, and a resolver (`setScorerResolver` / `setDisplayResolver` in `lib/http.ts`) that re-checks the link on every request. Put new secret body fields under a redacted name (`token`, `code`, `pin`, `password`).
- **Super Speakers origin** (S14f, D-157): the scorer app and the board may run on `SPEAKERS_ORIGIN`. Their endpoints must live under `/api/scorer…` or `/api/board…`: `route()` gives those paths the `speakers` origin class (main or speakers origin accepted), every other path only the main origin; never check origins by hand. Build scorer and board addresses from `config.origins.speakers` (everything else from `PUBLIC_ORIGIN` / `origins.main`). Decide which host a request is for with `isSpeakersHost(origins, req.headers)` (the raw `Host` header), never with `req.host` / `req.hostname`, which follow a client-supplied `X-Forwarded-Host` behind a trusted proxy. A new page or file the scorer app or board needs on the speakers host goes into the allow-list in `lib/speakersHost.ts` (and a page the main host should forward into its 308 list), with a case in `tests/server/speakers-origin.test.ts`.
- **School-wide modules** (S12, D-127): a module that is not switched per class+subject goes into `SCHOOL_MODULE_CATALOG` (`shared/modules.ts`); gate it with `isModuleAvailable(db, key)`, never `isModuleEnabled(db, contextId, …)`. It has no per-class `config`.
- **Server-Sent Events** (S12, D-134): a stream is a `rawRoute` that calls `reply.hijack()`, writes `text/event-stream` with `Cache-Control: no-store, no-transform` and `X-Accel-Buffering: no`, sends a heartbeat comment under 100 s, re-checks the session before every push, closes on `req.raw` `close` and registers its close function for the server's `onClose`. Send only a change signal (a version), never data; the client refetches the normal GET. The one exception is the assistant chat's run stream (S19b, D-180), which carries the answer as it is written: its events are parsed with the `AssistantRunEvent` allow-list on both sides.
- **Theme keys** (S14g, D-158): a theme key is a built-in key or the slug of an imported theme package (`Theme` in `contracts/school.ts`). Before writing a changed theme call `assertThemeUsable(db, key)` and when sending a stored key to a screen use `effectiveTheme(db, key)` (both in `modules/themes/service.ts`); never read `custom_themes` elsewhere. An editor gets the **stored** key (plus `isThemeUsable` as `themeAvailable`, or `chosenTheme` next to the shown theme) and its form sends `theme` only when the user changed it, so saving other fields never replaces an imported theme that is switched off (`ThemePicker switchedOff` explains it). Theme packages are checked only with `validateThemePackage` (`shared/themePackage/validate.ts`).
- **AI tools over MCP (S14h1, D-160, D-161).** An endpoint becomes an MCP tool only by declaring `mcp: { scope, tool, description, readOnly, cost? }` on its contract (only `classroom`, `teacher` and `admin` endpoints registered with `route()`; never exports, erasure, backups, credentials, link tokens, files, notes, levels or Secret Student data). The description is written for an AI client: what it returns and what is withheld. Client builds strip the `mcp` property from the contracts (`scripts/stripMcp.ts`, S14i), so keep it a plain object literal of literals and never read it in client code. Its output schema must mark every string that could hold personal data with `.meta(pii(kind))` (`shared/mcp.ts`; `LocalizedText` is already a label); `tests/server/mcp-privacy.test.ts` fails on an unmarked field and scans every tool's result for marker names and texts. Never return results to an AI client except through `privateResult` (the transport does it); never write `mcp_tokens` or `mcp_pseudonyms` outside `modules/mcp/` (the importer's revert only checks whether a student has a pseudonym). Take a user id from an actor with `actorUserId(ctx.actor)`, never `actor.type === 'user'`: an AI tool acts as `{ type: 'mcp', id, role, tokenId }` and its audit rows carry `via_token_id`. A hand-written tool (`modules/mcp/tools.ts`) calls endpoints through `callEndpoint`, so their checks run. A test that switches AI tools or student data on switches them off again in `finally`. **OAuth (S14h2):** OAuth access tokens are `mcp_tokens` rows of kind `oauth` whose `family_id` is the connection (`oauth_grants`); end connections only with `revokeGrants` / `revokeOAuthForUser` / `revokeAllOAuth` (`modules/mcp/oauth/store.ts`), which end their tokens, codes and waiting requests too, and add any new way an account loses its sign-in to `revokeAllUserMcpTokens`. Redirect addresses are checked only with `checkRedirectUri` / `matchRedirectUri` (`oauth/redirects.ts`); an error before the client and its redirect address are validated is shown on our own page, never redirected. A Client ID Metadata Document is read only through `AppDeps.clientMetadataFetch` / `fetchClientMetadata` (allowed hosts, public addresses, no redirects, size and time caps). OAuth secrets (codes, verifiers, access and refresh tokens) are never logged, audited or exported. **Connect an AI app (S19c, D-181):** the setup page and its "Check connection" read only what exists (the call log `mcp_calls`, tokens, connections, the allowed hosts); never add tracking of what an app asked or got. An app's documented OAuth return host goes in `AI_APP_RETURN_HOSTS` (`shared/mcp.ts`) and its recognition in `appOfConnection` (`modules/mcp/setup.ts`); adding a host to the allow-list stays the administrator's click.
- **Assistant connections (S19a, D-179).** Model providers are reached only through `streamChat` (`server/modules/aiConnections/provider.ts`) and `aiRequest` (`http.ts`): addresses pass `checkBaseUrl` and the policy lookup, redirects are not followed, calls are time- and size-limited. Connection secrets are sealed, never returned, logged, audited or exported; a provider's error text is never passed on, only an `AI_FAILURES` code and the HTTP status. Count usage with `recordTokens` and check limits with `beginAssistantMessage`. Load a connection only through `loadManaged` / `connectionForUse` (another user's connection is a 404). Tests never reach a real provider: point `aiProviderUrls` at `tests/ai-fake.ts` and use its fake keys.
- **Assistant chat (S19b, D-180).** The chat runs on the server (`server/modules/assistantChat/`) and reaches student data only through `server/modules/mcp/assistant.ts`: tools are the teacher-role MCP tools (plus `read_guide`), run with `runAssistantTool` (`callEndpoint`, the endpoint's own checks, `privateResult`) as the MCP actor with `tokenId: 'assistant:<chatId>'`; never call a service directly from the loop. **Confirmation:** a tool with `readOnly: false` never runs from a model reply; it is stored `pending` and runs only from the teacher's answer endpoint, which takes Yes or No for one chat, message and call and runs the stored arguments (never arguments from the client), claimed once in a transaction. Unknown tools, other roles' tools and bad arguments are `refused`; a change is checked against its tool's schema before it gets a card, a change whose free text holds a pseudonym (`Student N`, `student-N` outside an id field) is refused, and call ids are made unique within the chat before they are stored. **Cards say it in words:** the card shows the tool's label (`assistantChat.tool.<name>`), each argument's label (`assistantChat.arg.<key>`; a new change tool needs both, `tests/server/assistant-chat-review.test.ts` checks), ids as the teacher's own things (`CardLookup`), free text exactly as it will be written (never through `toBrowser`) and lists in full, one item per line. **Pseudonyms:** everything to the provider passes `assistantPrivacy(...).toProvider` (and the tool results `privateResult`); store messages as sent and put names back only with `toBrowser` on the way to the browser; history goes to the provider through `providerRowOf` (named texts scrubbed, named tool results and tool-call arguments withheld once student data is off); every round of a run re-checks the switches and the mode (`stopReason`) before anything more leaves; scrub with `scrubStudentFromChats` when a student is erased. **Untrusted data:** tool results go to the model with the data notice (`RESULT_PREFIX`) and students' text only as `untrustedText`; the system prompt says both are never instructions; never let a tool result decide what runs without a card. Count every message with `beginAssistantMessage`; show provider failures only as `AI_FAILURES` codes. A test that switches the chat, AI tools or student data on switches them off in `finally`; tests script the model with `tests/assistant-fake.ts`.
- **Conditional GET** (D-045): an endpoint that is polled sets an `ETag` header and answers `reply.code(304).send()` to a matching `If-None-Match` (see `modules/lessons/routes.ts`); the client polls it with `callConditional(ep, input, etag)`. A `teacher`/`admin`/`account` endpoint that a screen polls on its own (not on a user action) is declared `background: true` (S14e3): it still needs the classroom PIN unlock but never slides its inactivity window (PIN-7).
