## S2 — 2026-11-07
- **D-020** — In classroom mode with the PIN lock engaged, every `teacher`/`admin`/`account` endpoint answers **423 PIN_REQUIRED before the role check**, so a locked device responds the same way to every sensitive URL (PIN-8). Role errors (403) apply once unlocked. — Decided by Claude.
- **D-021** — Enrolment dates: `fromDate` inclusive, `toDate` exclusive (the day the student left / joined the next class). A move/promotion closes **every** open enrolment of the student and opens one in the target class; the default date is today in the target class timezone, or the target year's start date if that is later. Archived years refuse both closing and opening enrolments (unarchive first). Promotion must target a class in a *different* year; moves within a year use `/api/admin/students/move`. — Decided by Claude.
- **D-022** — Duplicate students: a matching student number is a hard conflict (409 `STUDENT_NUMBER_TAKEN`); a matching folded name is a warning (409 `POSSIBLE_DUPLICATE`) that the caller overrides with `allowDuplicateName: true` after confirming it is a different child. Never merged automatically (IMP-4). Teachers only see candidate names from classes they teach; other matches are reported as a count (ACC-4). — Decided by Claude.
- **D-023** — Admin clearing a teacher's PIN also revokes that teacher's sessions (a locked classroom device must not stay unlockable-by-nobody or become unlockable without a PIN). Admin password reset and account deactivation revoke sessions too. An admin cannot deactivate their own account or the last active admin, and resets their own password via "change password". — Decided by Claude.
- **D-024** — `seed:demo` runs only outside production on a database without school data. If accounts already exist (e.g. created with `admin:create`) it requires `--force-demo` and never touches existing logins. Demo passwords are random per run and printed once. — Decided by Claude (interpretation of the S2 brief).
- **D-025** — Terms are calendar configuration (no records reference a term id), so admins may delete them while the year is writable; school years, classes and subjects are only archived. New accounts start in the school's default language; afterwards the language is per user (UX-4). — Decided by Claude.
- **D-026** — Module availability: the 8 teacher modules default to enabled; `media.studentPhotos`, `media.evidencePhotos`, `media.evidenceAudio` default **disabled**, `media.evidenceDocuments` enabled (D-014). Rows are seeded at startup; code falls back to the same defaults. Effective = admin availability AND the teacher's per-context switch (no row = on). Turning anything off only flips flags; teacher config and data stay (CFG-2). — Decided by Claude.

## S2 review fixes — 2026-11-07
- **D-027** — Enrolments are **date-aware** (refines D-021). An enrolment counts on local day D when `fromDate <= D < toDate` (open when `toDate` is null), with D = today in the class timezone (`enrolmentActiveOn`). Rosters, class student counts and levels use it, so a move or promotion dated in the future keeps the student in the old class until that day and the new class fills on that day. The move/promotion date (default: today, clamped into the target year) must lie inside the target class's school year (`MOVE_DATE_OUTSIDE_YEAR`); across years the old enrolment ends no later than the day after its own year ends (a promotion dated 1 September closes June's class on 1 July, not over the summer). New enrolments default to today clamped into the class's year. Moving students **out of** an archived class is refused like moving into one (`CLASS_ARCHIVED`; unarchive first). School years may not overlap, and a year's dates cannot change so that its terms or enrolment start dates fall outside it. Teachers may edit a student in their current class or one the student is scheduled to join; admin class/year filters show current and scheduled students. — Decided by Claude.
- **D-028** — Duplicate warnings (refines D-022) also run on **rename** (`allowDuplicateName` on the update) and include **deactivated** students (`candidates[].active = false`, `inactiveMatches` count), so a returning child is reactivated instead of getting a second identity. — Decided by Claude.
- **D-029** — Unused password-reset links are voided whenever the account's email changes, an admin resets the password, the user changes their own password, or the account is deactivated (D-015). SMTP on any port other than 465 requires STARTTLS (`requireTLS`), certificates are verified, TLS ≥ 1.2. — Decided by Claude.
- **D-030** — `seed:demo` hashes the demo passwords first and then writes the accounts and all school data in **one transaction**: a failed run leaves nothing behind and can simply be re-run (refines D-024). — Decided by Claude.

## S3 — 2026-11-07
- **D-031** — **Classroom mode needs a PIN.** `/classroom` only opens for a teacher who has set a PIN; without one it shows "set a PIN first" with a link to the profile, because a classroom display that cannot be locked would expose the teacher area (PIN-1). Administrators are sent to `/admin` (they do not teach). — Decided by Claude.
- **D-032** — Client side of the PIN lock (PIN-2…6): the client never compares `pinUnlockedUntil` with its own clock; the server returns `me.pinUnlocked` (clock skew on classroom PCs is common). After an unlock the **teacher menu is shown first** even when the lock screen was reached from a deep link (a session flag cleared by the menu), so no sensitive page flashes onto the display. The teacher/admin area relocks after **3 minutes without input** on the client (`CLIENT_IDLE_LOCK_MS`), on top of the server's sliding 5-minute window, and any 423 swaps to the lock screen and purges `['sensitive', …]` caches. A bfcache restore purges them too and re-runs the guards. — Decided by Claude.
- **D-033** — `seed:demo` accepts a fixed password (`CC_DEMO_PASSWORD`) **only when `NODE_ENV=test`** and only with ≥ 10 characters, for the Playwright server. Every other run keeps random passwords (D-024). — Decided by Claude.
- **D-034** — `/dev/catalog` (component catalogue with all themes × languages, 20/34-card grids, 200 % text) is available to any signed-in user in every build. It contains only fictional fixture data and calls no API, so shipping it costs nothing and lets the owner check themes on the real classroom screen. — Decided by Claude.
- **D-035** — Outbox semantics (ENG-4, UX-10/11): a command is written to IndexedDB before it is sent; commands for one device are sent in order, at most one flush at a time (Web Locks across tabs); network/5xx/429/423 failures retry with exponential backoff (1 s → 30 s), 401 pauses the queue until the next sign-in, a server rejection moves the command to the needs-attention tray. **Retry from the tray re-queues it under a new opId**, because the server records rejected opIds and would otherwise replay the same rejection; dismiss drops it. The outbox is in place for S5, which adds the lesson commands that use it. — Decided by Claude.
- **D-036** — UI kit choices: React Aria Components for buttons, text fields, switches, dialogs and tabs (keyboard, focus and screen-reader behaviour), but a **native `<select>`** for choices — it is the most reliable control on classroom touch screens and phones and needs no custom popover. Toggles always show "On/Off" text next to the switch (status not by colour alone). Status chips use icon + text + pattern. Classes with more than 24 students switch the student grid to a compact density so 34 cards fit on one 1920×1080 screen. — Decided by Claude.
- **D-037** — E2E tests run against a throw-away server (temp data directory, `NODE_ENV=test`, fixed test pepper, demo seed with D-033) on Chromium: a 1920×1080 touch "classroom display" project and a Pixel 7 project for tests tagged `@mobile`. Accessibility is checked with axe (default rule set incl. colour contrast) per theme; there is no pixel-diff screenshot baseline yet. CI runs the suite on Ubuntu. — Decided by Claude.
- **D-038** — Administration screens and the catalogue are lazy-loaded chunks; the classroom and teacher area stay in the main bundle so they keep working if the connection drops during a lesson. — Decided by Claude.

## S3 review fixes — 2026-11-07
- **D-039** — **The outbox belongs to an account** (refines D-035). Every queued command stores the user id that queued it; only that account's commands are sent, counted, shown in the needs-attention tray or dismissable, and the batch carries `asUser` so the server refuses it with 409 `WRONG_ACCOUNT` when another account's cookie is in use. The owner follows the `me` query (sign-in, sign-out, 401, account switch). Other accounts' commands stay parked on the device until their owner signs in again; they are never sent under another session and never discarded automatically (UX-11). Commands rejected with `OP_ID_REUSED` (the server may already have applied them) or `UNKNOWN_COMMAND` can only be dismissed, not retried under a new opId. Command rejections carry a machine-readable `reason` that the tray translates; the server's English message is diagnostics only. — Decided by Claude.
- **D-040** — **Temporary passwords are enforced by the server.** While `mustChangePassword` is set, every `classroom`/`teacher`/`admin`/`account` endpoint answers 403 `MUST_CHANGE_PASSWORD` (after the PIN check, D-020), except endpoints marked `allowWithTemporaryPassword` (only `POST /api/auth/password`). `user` endpoints (me, logout, lock/unlock, preferences) stay open. The client sends the user to `/change-password` on that reason, and the outbox pauses instead of parking commands. — Decided by Claude.
- **D-041** — PIN lock screen details (refines D-032): the server returns the lockout as a relative `retryAfterMs` (plus `retryAt` for logs) and the client counts down from when it received the answer; wrong-PIN answers include `triesBeforePause` and `attemptsBeforeSignOut`, and from the first pause on the lock screen warns how many wrong PINs remain before the session is signed out. "Menu first" (PIN-4) also holds in other tabs: a sensitive area that has shown the lock screen and then sees an unlocked session goes to the teacher menu instead of revealing the deep-linked page. Toasts are sensitive unless raised with `scope: 'classroom'` and are cleared on lock, on entering the classroom and on sign-out; a toast with an active undo is never evicted by newer toasts (UX-9). — Decided by Claude.

## S5 — 2026-11-07
- **D-042** — **A lesson is created by one idempotent `lesson.start` command whose opId becomes the lesson id.** At most one active lesson per class+subject (partial unique index). Starting while one is running today returns `ok` with `{started: false, reason: LESSON_ALREADY_ACTIVE, lessonId}` and ignores the routine choice, so a double tap, a second device or a replay never creates a second lesson; the device simply resumes the running lesson (LES-2, UX-11). Its start-screen attendance is still applied (refined by D-053). — Decided by Claude.
- **D-043** — **Lessons belong to their local day.** A lesson still active after the end of its local day (class timezone) is no longer shown on the dashboard; the next start in that class+subject marks it `abandoned` (not ended, data kept, audited with reason `next_day`). Queued commands may still target it by id until then. Consequence: a lesson that runs across local midnight disappears from the dashboard at midnight. — Decided by Claude.
- **D-044** — **Commands name their lesson.** Every lesson/attendance command carries `contextId` and `lessonId`; the server refuses it with `WRONG_LESSON` when the lesson is not the active lesson of that context (or the envelope's context/lesson disagree with the payload) and with `LESSON_ENDED` when the lesson has ended. Commands queued for class A therefore never land in class B after a switch (LES-4). — Decided by Claude.
- **D-045** — **Polling with ETags.** `GET /api/classroom/contexts/:id/lesson` answers 304 to a matching `If-None-Match`; the ETag combines the lesson version (bumped on every change), the local date and a hash of the day's attendance rows, so a colleague's attendance change also refreshes the screen. The client (`callConditional`) polls every 5 s and the active-lesson list every 15 s; polling pauses while this device has unsent commands so a stale server answer never overwrites an optimistic change, and the lesson is re-read once the outbox is empty. — Decided by Claude.
- **D-046** — The classroom roster for lessons returns only classroom-safe fields plus attendance (no notes, no levels); attendance notes are teacher-area only. — Decided by Claude.
- **D-047** — **Routine snapshot.** The routine (name + stages) is copied into the lesson when it starts; later template edits, archives or default changes apply from the next lesson only (RTN-2). The built-in default routine (RTN-1, EN/TR names) lives in code (`builtin:default`), is always usable and cannot be edited, only copied. With the Routines module off, lessons start with an empty routine and stage commands answer `FEATURE_DISABLED`. — Decided by Claude.
- **D-048** — **The classroom timer is a core lesson tool**, not part of the Routines module: server-held state (duration, running, startedAt, remaining) shown from the server clock offset so all devices agree; when time is up the panel changes once (border, text, icon — no flashing) and one soft tone plays only if both the class and the device allow sounds. — Decided by Claude.
- **D-049** — **Attendance model.** Daily attendance is one row per student and local day, shared by every teacher of the class; any change is audited (`attendance_daily`, with before/after and actor, ACC-9). A lesson exception overrides it for one lesson only (effective = exception › daily › not recorded). "Not recorded" is never counted as present. The start screen proposes "present" for everyone without a record (a colleague's earlier record is kept) and sends only the changed rows (refined by D-053); "Everyone else present" never overwrites an existing record. — Decided by Claude.
- **D-050** — Classroom attendance commands need an active lesson (they are lesson-scoped and refused otherwise). Corrections for other days go through the teacher area (`/teacher/attendance`, PIN-gated REST endpoints) for any day inside the class's school year; history ranges are limited to one year. Teachers see exceptions only for their own lessons. — Decided by Claude.
- **D-051** — **End Lesson is a registry of steps.** The server keeps an ordered registry (`registerEndLessonStep`) whose validated inputs arrive in one `lesson.end` command; the core step is the reflection (rating 1–4 or none, optional note, order 100), so End Lesson works with every optional module off (LES-3). S7 adds the Secret Student reveal and outcome steps before it; the client mirrors this with `registerEndStepUi`. — Decided by Claude.
- **D-052** — **Dashboard slots and start steps are registries too** (`registerDashboardSlot`, `registerStartStep`, client side). A slot or step appears only when its module is enabled for the class+subject and has registered a component; until S6–S8 register theirs (assistant, counter, Secret Students, groups, homework) they are simply omitted — no "coming soon" placeholders on the classroom screen. — Decided by Claude.

## S5 review fixes — 2026-11-07
- **D-053** — **Start-screen attendance is never dropped and never overwrites newer records silently** (refines D-042, D-049). `lesson.start` carries only the students the teacher tapped, each with the daily status the screen showed (`expected`), plus `othersPresent: true`. The server writes an entry only if the record still has that status (or already has the new one); otherwise it keeps the colleague's record and counts it in `attendanceKept`, which the device shows as a warning toast naming the class. `othersPresent` marks present only students who still have no record when the command runs (same rule as "Everyone else present"). This applies on both paths: a new lesson and `LESSON_ALREADY_ACTIVE` (second device, two opIds), because the attendance is shared daily data for today and the teacher owns the context. Replays of the same opId still return the stored result without effect. — Decided by Claude.
- **D-054** — **Per-class flow drafts** (LES-4): the classroom page keeps the Start Lesson draft (step, tapped statuses, routine) and the End Lesson draft (step values, tied to the lesson id) in its per-context screen state, and the flows are keyed by context (and lesson), so switching away and back restores them and nothing typed for one class can be sent for another. — Decided by Claude.
- **D-055** — The classroom-access lesson summary (`GET /api/classroom/lessons/:id/summary`) serves only lessons of a teaching context the teacher still holds, and includes the private reflection note only for a lesson of the class's current local day (the summary shown right after End Lesson). Older notes are teacher-area data (PIN-1/PIN-8). Teacher-area exception edits likewise require the teacher to still hold the lesson's context (`assertOwnsContext`, ACC-10). — Decided by Claude.
- **D-056** — Timer details (refines D-048): Start on a timer that ran out (stored as `running` with 0 left) restarts it from its full duration on the server and on the device. The tone plays only when the countdown reaches 0 while the dashboard watches it (or within 3 s of the end), so a reload, another device or re-opening the dashboard never replays it. — Decided by Claude.
